# AI Knowledge Inbox

A small single-user web app: save notes and URLs, then ask questions over
your saved content. Answers are generated by a simple RAG (retrieval-augmented
generation) pipeline and returned with cited sources.

Runs entirely on your machine. The only external call is to the Google Gemini
API (an "OpenAI-equivalent" LLM API) for embeddings and chat completion.

---

## Stack

| Layer     | Choice                                              |
| --------- | --------------------------------------------------- |
| Backend   | FastAPI (Python), Uvicorn                           |
| LLM       | Google Gemini via OpenAI-compatible endpoint        |
|           | `text-embedding-004` (embeddings) + `gemini-2.0-flash` (chat) |
| Storage   | SQLite (items + chunk embeddings)                   |
| Retrieval | In-memory brute-force cosine (NumPy)                |
| Frontend  | React + Vite + Tailwind                             |

The `openai` Python package is used as the client, pointed at Gemini's
base URL — swapping to OpenAI proper is a two-line change (base_url + key).

## Run

### Backend

```bash
cd backend
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Create `backend/.env` (copy the example):

```bash
cp .env.example .env
# then edit .env and paste your key:
# GEMINI_API_KEY=your-actual-key
```

Start it:

```bash
uvicorn app.main:app --reload
```

- API: http://localhost:8000
- Interactive docs: http://localhost:8000/docs
- Health check: http://localhost:8000/health

On startup you should see `vector index loaded: N chunks` in the logs.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173.

## Project structure

```
backend/
  app/
    main.py          # FastAPI app, routes, middleware, error handling
    config.py        # env + tunable settings
    db.py            # SQLite connection + schema
    models.py        # Pydantic request/response shapes
    ingest.py        # URL fetch + chunking
    embeddings.py    # embedding calls (Gemini, OpenAI-compatible)
    store.py         # in-memory vector index (load / add / search)
    rag.py           # retrieve -> build prompt -> generate answer
    logging_conf.py  # structured logging
  requirements.txt

frontend/
  src/
    api.js               # fetch wrappers for the 3 endpoints
    App.jsx              # composes UI, owns shared item list
    components/
      AddItem.jsx        # note/URL input -> POST /ingest
      ItemList.jsx       # GET /items
      AskBox.jsx         # POST /query -> answer + sources
```

Each module has one job. Vector search lives in `store.py`, not smeared across
`rag.py`; `main.py` holds only routing and cross-cutting concerns (logging,
error handling).

## API

### `POST /ingest`

```jsonc
// note
{ "source_type": "note", "content": "some text" }
// url
{ "source_type": "url", "url": "https://example.com" }
```

Response `201`: `{ "item_id": 1, "chunks": 3 }`

### `GET /items`

List saved items, newest first.

### `POST /query`

```json
{ "question": "what did I save about X?" }
```

Response `200`:

```json
{
  "answer": "…",
  "sources": [
    { "item_id": 1, "source_type": "note", "source": null, "snippet": "…", "score": 0.82 }
  ]
}
```

### Status codes

| Code | Meaning                                           |
| ---- | ------------------------------------------------- |
| 201  | item created                                      |
| 200  | query answered / items listed                     |
| 400  | bad input (missing content/url, empty after chunk)|
| 422  | schema validation failure (Pydantic, automatic)   |
| 502  | upstream failure (URL fetch or LLM)               |
| 500  | unexpected error (logged server-side)             |

Every request gets an 8-char ID, logged at start/finish with status and
latency, and returned in the `X-Request-ID` header so a client error maps to a
server log line.

## How the RAG pipeline works

1. **Ingest** — a note (or URL's extracted text) is split into chunks.
2. **Embed** — each chunk is embedded into a vector.
3. **Store** — chunk text + embedding go into SQLite; the vector is also added
   to the in-memory index.
4. **Query** — the question is embedded, compared against all chunk vectors by
   cosine similarity, and the top-k chunks are retrieved.
5. **Generate** — retrieved chunks are stuffed into the prompt as context; the
   LLM answers using only that context.
6. **Cite** — the retrieved chunks are returned alongside the answer as sources.

Tunable in `config.py`: `chunk_size`, `chunk_overlap`, `top_k`, model names.

## Tradeoffs

### Chunking approach

Fixed-size character windows (500 chars, 50 overlap). Deterministic, trivial to
reason about, no dependencies. The overlap reduces the chance of splitting a
relevant idea cleanly in half at a boundary. Cost: it can cut mid-sentence and
is blind to document structure. For production I'd move to token-aware,
recursive splitting on natural boundaries (paragraphs -> sentences) and size by
tokens rather than characters to match the embedding model's real unit.

### Vector store choice

SQLite holds both the raw items and the chunk embeddings (embeddings as JSON).
Similarity is brute-force cosine over an in-memory matrix loaded once at startup
and appended to on ingest. One file, zero infrastructure — the right amount of
machinery for a single-user app at this scale, and brute force returns exact
nearest neighbours (no approximation error). Keeping items and vectors in the
same store also makes source citation trivial: each chunk carries its
`item_id`, so answers link straight back to the original.

### What breaks at scale

- **Memory** — the whole embedding matrix lives in RAM. Fine for thousands of
  chunks; at millions it won't fit.
- **Search cost** — brute-force cosine is O(n) per query; latency grows linearly
  with the number of chunks.
- **Single process** — the in-memory index is per-process; two workers would
  hold divergent indexes.
- **Startup** — the index rebuilds from SQLite on every boot; slow once large.
- **Concurrency** — SQLite is fine single-user, poor for many concurrent writers.

### Production changes

- **Vector store** — move embeddings to a real ANN index (pgvector, Qdrant);
  keep relational items in Postgres.
- **Chunking** — token-aware recursive splitting; version the model + strategy
  so the index can be rebuilt when either changes.
- **Ingestion** — fetch + embed asynchronously via a job queue so `/ingest`
  returns immediately instead of blocking on the network.
- **Resilience** — retries with backoff on LLM calls; timeouts; circuit breaker.
- **Ops** — request tracing/metrics, rate limiting, and (once multi-user) auth
  plus per-user data isolation.
- **Deployment** — SQLite is a local file; on ephemeral hosts it resets on
  redeploy, so a hosted app moves the store to Postgres/pgvector.

## Notes

- No auth — single-user by design, per the assignment scope.
- Each user supplies their own free Gemini key in `backend/.env`
  (`.env` is gitignored; `.env.example` shows the shape).
- To use OpenAI instead of Gemini: change `base_url`, `embed_model`,
  `chat_model` in `config.py` and the key name in `.env`.
